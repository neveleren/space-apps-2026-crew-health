# Architecture: how a reading becomes a message

How a reading travels from a device or a person, through the machine and the levels, to what the astronaut sees; what is saved where; and how to add a measure or a device. Version 1.2.0 (see `VERSION`).

Written by Claude (Anthropic), an AI system, for team Just For Fun. The idea, the structure and every decision belong to the team's human member; the code was generated by Claude. The code wins over this page: where they differ, this page is out of date.

## In one minute

- Every reading, periodic review, message to a doctor and crew alarm line becomes an **event**: one JSON object with a kind, a time, a person and, on all but alarm lines, the position of the simulation switches. The private journal, the plan for hard days and the PIN are not events: they stay in the browser.
- **For an analog test** such as NASA's HERA, each step in the life of an alert on a person's screens (shown, acknowledged, read, cleared, false alarm, a Bedford workload rating) is an event of kind `alert` in that person's own record (`src/alert-log.js`), and a **drill** marks every new event with the time it started (`src/drill.js`): its alarms sound and reach the crew and the doctor as usual, but its readings never reach the machine the screen judges the person by.
- **The machine runs in the browser** (`src/engine.js`). It puts each reading in its **cell** (`src/config.js`), compares the value with the cell's norm and red limits, and records who gets it. No AI model is connected in this version: "the AI takes it" is a route the machine records, not a call to a model.
- **The levels** (`src/state-levels.js`) turn one person's history into today's sentence: fine, attention, needs action or urgent, plus notes such as stale data.
- **Two screens** draw from the machine: the crew screen (`index.html`, `src/crew.js`), which also uses the levels, and the technical view (`machine.html`, `src/ui.js`), which shows the machine's own routes and the straight-line forecast (`src/trend.js`) but not the levels.
- **The server** (`serve.mjs`) serves the pages, checks every event with the rules in `src/security.js`, appends it to a plain file per person and seals each message to a doctor in the outbox. It never judges a reading.
- **Nothing is fetched from the internet** unless the person turns on one of the two Earth demos (ISS cabin air, space weather).

## Data flow

```
 a device, a file, a feed or the person
   |   ble.js, csv-import.js, isslive.js, quicklog.js, the forms and buttons of crew.js and ui.js
   v
 reading { source, indicator, value, time }
   |   crew.js addReading(), integrations.js toEvents() and onlyNew()
   v
 event { v: 1, kind: "reading", time, person, state, reading }
   |                                      |
   | machine.receive()                    | store.append()
   v                                      v
 engine.js: cell, norm, red limit,      store.js: POST /api/events
 route, this person's history           serve.mjs: security.js check, then data/<person>.jsonl
   |                                    (a message to a doctor is also sealed in data/outbox/)
   v
 state-levels.js assess(): levels, items, fresh data, ship alarms
   |
   v
 crew.js: the dated sentence (headlineFor), chips, rows, messages, status line, alert tones
```

### Opening the crew screen

1. The person picks a sign-in card: one of four made-up example crew members or one of four real Inspiration4 participants. If a PIN is set for that card, it is asked first (`src/privacy.js`).
2. `openStore({ person })` asks `/api/events?person=<id>`. The answer holds this person's events, the ship's cabin readings and every crewmate's alarm lines, nothing else.
3. `rebuild()` in `src/crew.js` makes a fresh machine and sends it, in time order, the example flight (when the "example flight" switch is on; made up and marked `example: true`) and every saved reading and review. The machine's history is never saved by itself: it is rebuilt from the events each time.
4. `assess()` and `headlineFor()` give the dated sentence (for example "As of <date>, your physical condition needs attention, your mental condition is excellent."); `render()` draws the screen.

The technical view opens the store for everyone (`openStore()`, which reads `/api/events?all=1`): the engineering view, which a real deployment would restrict.

### A new reading

1. A source makes a reading: a Bluetooth device (`connectHealthDevice()` in `src/ble.js`), a CSV file (`importCsv()` in `src/csv-import.js`), the ISSLive feed (`readCabinAir()` in `src/isslive.js`), a hand-entry form on a measure page, the daily check-in, a quick log (`src/quicklog.js`), the reaction test, an eye self-check answer, the camera, or the Help key (held for 2 s, it records `chest_grab_help` through the camera cell).
2. Device, form, log, test, camera and Help key readings go through `addReading()` in `src/crew.js`: it wraps the reading as an event, sends it through `machine.receive()` and saves it with `keep()`, which calls `store.append()`. Feed and file readings take another path: `onlyNew()` leaves out a value already saved (same person, source, measure and time), `toEvents()` makes the rest events, `keep()` saves them and `rebuild()` sends everything through a fresh machine.
3. If a reading leaves the person with an urgent item (a red limit, or a camera or Help key alarm), `shareCrewAlarm()` saves one `alarm` event with a single line, "<name> needs help now: <measure> <value> <unit>." (for the Help key: "<name> pressed the Help key."), and a `report` to the doctor with the topic `alarm`, written by the program: to the doctor on board, or sealed in the outbox for Earth. A new line is written only when the set of urgent signs changes (`needsNewLine` in `src/crew-alarm.js`). When the last sign ends, or the person presses "I am okay: false alarm", it saves an all clear, `{ text, clear: true }`, and a report with the topic `alarm-clear`. Never for the ship or a real Inspiration4 participant. A CSV import shares alarm lines too.
4. While someone is signed in, the screen asks the server for that person's events every 15 s (`ALARM_RULES.pollSeconds`, a draft). New crew lines and ship readings redraw the banner, the Messages key and Today, and a new crewmate line sounds. An urgent alarm repeats its tone every 4 s and its spoken line every 16 s until someone acknowledges it.
5. A save the server refused leaves the screen again, and the screen says so. When the server does not answer, what was entered waits in this browser (`jff-crew-waiting-v1`) and is sent when it answers again.
   - The same look at the server brings the steps of the person's alert log written on their other screens (`newOwnLog` in `src/alert-log.js`): what one screen acknowledged stops sounding on the others within 15 s, and what it marked as read no longer counts as new there.
   - While a drill runs (`ui.drill`), `addReading()` puts the reading into a second machine, `drillMachine` (the record plus that drill's readings), never into `machine`; `alertsFor()` adds the alerts only the drill machine has, as "Drill: ..." with their own ids, and `shareCrewAlarm()` writes the line "DRILL: ..." and a message "DRILL. ..." from it. A line is never marked as a drill while a real urgent sign from before the drill is present; "I am okay: false alarm" on a real alarm is saved unmarked, into both machines (`addReading` with `real`), and its all clear stays real. Ending the drill (the switch, "End the drill", sign-out or 60 minutes, a draft) writes the drill line's all clear.
6. The screen redraws.

### Routes in the machine (`src/engine.js`)

Each result keeps a list of steps with codes. A step marked `by: 'open'` stands for something the team has not decided; most of them name one of the team's open questions (`question`, a number in `QUESTIONS` of `src/config.js`). The code does not guess those answers.

| Cell kind | What the machine checks | Status | Who gets it |
|---|---|---|---|
| `number` | the value against the norm (`checkNorm()`: `range`, `below-both`, `min-parts`, `baseline-percent`), then the red limits (`redLimitOf()`) | `ok` or `out` | In the norm: nobody (`none`). Outside: the AI (`ai`) while the AI switch is on, otherwise `undecided` (open question 4). Past a red limit: `crew-alarm`, by automation and never the AI: the person and the crew (the crew medical officer for "needs action"), then the doctor on board, the doctor on Earth over the link, or a queued message when there is no link. A cabin value past its limit is the ship's alarm on every screen, with no doctor. |
| `number`, norm type `record` (body mass, exercise, reaction time) | only that the number can be read | `recorded` | nobody |
| `number` marked `atRest` (heart rate, breathing rate), reading marked `context: 'exercise'` | not judged against the resting norm; only red limits not marked `atRest` still count | `recorded`, or `out` past such a limit | nobody, or `crew-alarm` past such a limit |
| `panel` (blood tests) | each analyte against the lab's own range (`checkPanel()`) | `ok` or `out` | outside: the AI, or `undecided` with the AI off |
| `complex` (X-ray, ECG, ultrasound, OCT scan) | that something came in | `analysis` | the AI (open question 3), or `undecided` with the AI off |
| `camera` | the trigger: `sleeping` and `chest_grab_ok` are ignored; `chest_grab`, `chest_grab_help` and `chest_grab_no_answer` raise the alarm | `ignored` or `out` | the doctor on board, else the doctor on Earth, else (no doctor and no link) the crew on board with the doctor's message queued: a draft for open question 5 |
| `self-report` (mood, energy, sleep quality, thinking test, cycle, topics, symptoms, medicines, eye self-check) | not empty, on its scale, on its list (`checkSelf()`) | `recorded` | nobody; mood and energy, and the hours of sleep, also wait in this person's pile for the periodic review |
| a `review` event | the pile of self-reports since the last review | `analysis` or `empty` | the AI (open question 8), or `undecided` with the AI off |

A reading with no known person, no cell or a value the machine cannot read is `unknown`, goes to `undecided`, and is not added to the history.

### Levels (`src/state-levels.js`)

Every threshold here is a draft (`RULES` and `EXPECTED`, with the reasons in `RULE_NOTES`); the team and the flight surgeons decide. The colours follow NASA-STD-3001 Vol 2 (Table F.5-1), and colour is never the only cue: each level has its own icon shape and word.

| Level | Colour | Comes from |
|---|---|---|
| fine | none | nothing to report. A change that flight studies call common is information on the measure's page only: in flight, body temperature above the usual range by up to about 1 °C (a rise that builds up over the first 75 days) and below 38.0 °C, or a night of 5 hours of sleep or more. |
| attention | blue | a measure taken daily outside the norm 3 readings in a row; two or more vital signs (breathing rate, blood oxygen, blood pressure, heart rate, temperature) outside together within 24 hours, at once; a measure taken less often than daily (not daily in `EXPECTED_EVERY_DAYS`), at its first reading outside; a forecast crossing, only for a slow measure or a clear trend; mind: bad mood or low energy on 6 of the last 14 days |
| needs action | yellow | a red limit of level "action"; 7 daily readings in a row outside the norm (3 for a measure taken less often); a NASA standard missed (own pre-flight percentage, career radiation); mind: bad mood or low energy on 8 of the last 14 days |
| urgent | red | a red limit of level "urgent"; a camera or Help key alarm in the last 24 hours |
| stale (a note, not a level) | cyan | no reading for twice the expected interval. With no fresh data the sentence says "not enough fresh data", never "excellent". |

Two more rules: a reading taken during exercise that was only recorded never changes the judgement of the person at rest; a run outside the norm that holds a reading past a red limit is never waited on. The ship is assessed on its own (`assessShip()`); only a cabin value past the ship's own limit reaches each person's sentence, as "Ship caution" or "Ship emergency".

## Event schema

The server accepts an event only when it looks exactly like what the screens send (`eventProblem()` in `src/security.js`) and stores only the checked fields, in a fixed order (`cleanEvent()`). The same checks, except the one for future times, run again on every line read back from a file.

### Fields of every event

| Field | Needed | Rule |
|---|---|---|
| `v` | yes | the number 1 |
| `kind` | yes | `reading`, `review`, `report`, `alarm` or `alert` |
| `time` | yes | UTC in the form `Date.prototype.toISOString()` writes, the milliseconds optional, for example `2026-11-15T01:45:00.000Z`; when saved, at most 5 minutes ahead of the server's clock (draft) |
| `person` | yes | an id of lower-case letters, digits and hyphens, at most 32 characters, starting with a letter or digit; the program uses `crew-1` to `crew-4`, `ship` and `i4-c001` to `i4-c004` |
| `state` | no | `{ aiWorks, doctorOnBoard, linkToEarth }`, each true or false: the simulation switches at that moment |
| `example` | no | true or false; true marks made-up example data |
| `drill` | no | the ISO time the drill it belongs to started (`src/drill.js`), never after the event's own time; an event without it is not part of a drill |

No other field is accepted; only extra switches inside `state` (from an older saved screen setting) are dropped instead of refused. A request body may be at most 64 KB.

### The five kinds

| Kind | Own field | Rules |
|---|---|---|
| `reading` | `reading: { source, indicator, value, context?, detail? }` | `source`: a device id of lower-case letters, digits and hyphens, at most 64 characters. `indicator`: a measure of `src/config.js`. `value`: the shape the measure takes (next table). `context`: only `"exercise"`. `detail`: only on the reaction test reading (`indicator: "reaction"`): `{ median, lapses, falseStarts, count, durationS, mode, score }`, with `mode` required, `"full"` or `"demo"`, and the others numbers from 0 to 100,000 or left out. |
| `review` | none | the periodic review of one person's self-reports |
| `report` | `report: { to, text, topic? }` | `to`: `"doctor-onboard"` or `"doctor-earth"`. `text`: at most 6,000 characters. `topic`: optional, a short id (a lower-case letter, then letters, digits or hyphens, at most 32 characters). The crew screen sends `pmc` (the weekly conference summary), `alarm` and `alarm-clear` (written by the program), `letter-to-psychologist`, `talk-request` and `mind-checkins`. |
| `alarm` | `alarm: { text, clear? }` | one line of 1 to 200 characters, shown to every crewmate; `clear: true` marks an all clear, which takes that person's earlier line away. Each screen shows only a person's latest line, for at most 24 hours |
| `alert` | `alert: { id, step, level, system, private?, how?, rating? }` | one step of the alert log, kept in the person's own file and never given to a crewmate. `id`: the screen's id of the alert, of letters, digits and the signs `\|`, `:`, `.`, `_`, `-`, at most 160 characters (for example `crew-1\|red\|spo2\|3\|2026-11-15`, or `line\|crew-2\|crew-1\|<time>` for a crewmate's line). `step`: `shown`, `acknowledged`, `read`, `cleared`, `false-alarm` or `rated`. `level`: 1 to 3. `system`: `body`, `mind`, `camera`, `help-key`, `ship` or `crew`. `private: true` for an alert about the mind or a private measure. `how`, only and always on `acknowledged` and `read`: `mark-read`, `mark-all-read`, `messages-key`, `banner-silence` or `silence-all`. `rating`, only and always on `rated`: a whole Bedford rating from 1 to 10. No text of the alert |

### Reading values

| Measure | Value |
|---|---|
| a number measure (range, record, own pre-flight percentage) | a number, or a numeric text of at most 32 characters (the technical view sends typed numbers as text). Below zero only where the cell says `allowNegative` (cabin temperature, hearing threshold, OCT change). |
| blood pressure | `{ sys, dia }` |
| bone density | `{ hipSpine, neck }` |
| blood tests | `{ subject?, timepoint?, analytes: [{ code, name, test, value, min, max, units }] }`: at most 200 analytes, at least one that can be checked against its range |
| complex data | a text of 1 to 200 characters, for example `"image"` |
| camera | one trigger: `sleeping`, `chest_grab`, `chest_grab_ok`, `chest_grab_help`, `chest_grab_no_answer` |
| symptoms | `{ symptom, severity, note? }`: a symptom from the list, a whole number from 0 to 10 |
| medicines | `{ medicine, name, strength, amount, unit, takenAt? }`: a kit medicine, or `"other"` with a name; an amount above 0 and at most 10 |
| what is weighing on you | a list of topic ids, no repeats: `home`, `crew`, `ground`, `workload`, `sleep`, `monotony`, `health`, `nothing` |
| eye self-check | one of the four answers of the cell |
| sleep quality | a number from 1 to 7 |
| other self-reports | a short text (at most 200 characters) or a number |

## Storage

### Where the store keeps events (`src/store.js`)

| Store | When | What it means |
|---|---|---|
| `server` | the page came from our own server (`npm start`) | events live in `data/` on this computer |
| `browser` | the static copy, or no server answers | everyone's events under one browser storage key, `jff-health-events-v1`; a person's view is a filter, and saving writes the whole list back, so other people's events stay |
| `memory` | browser storage is blocked too | nothing is saved; the screen says so |

Whose events: one person, plus the ship, plus every crewmate's alarm lines. The ISS crew code of conduct (14 CFR 1214.403) says other crewmembers may not use or disclose a crewmember's medical information without consent, except as required for the immediate safety of the crew, so a crewmate learns only that someone needs help now.

### The server's interface (`serve.mjs`)

| Request | Answer |
|---|---|
| `GET /api/events?person=<id>` | that person's events, the ship's, and the alarm lines of everyone else, in time order |
| `GET /api/events?all=1` | every event (the technical view) |
| `POST /api/events` | `204` saved; `201` saved and queued in the outbox, with `{ outbox: { id, file, to, status, encrypted, kid, demoKey } }`; `400` not a valid event; `403` not from this program's own page; `413` larger than 64 KB; `415` not `application/json`; `503` a message to Earth with no outbox key |
| `GET /api/outbox?person=<id>` or `?all=1` | the queued messages without their sealed text |
| any other path | the program's files, `GET` and `HEAD` only; private folders are never served |

What is checked on every request, and what is not protected, is in `docs/SECURITY.md`. Settings: `PORT` (default 8080), `HOST` (default `127.0.0.1`), `HOSTS`, `DATA_DIR`, `OUTBOX_KEY_FILE`.

### Files on disk

| File | What it holds |
|---|---|
| `data/<person id>.jsonl` | one checked event per line, appended; named by id, with no personal information in the name. Read back line by line; a damaged line, or one filed under another person, is skipped. |
| `data/outbox/<time>-<random>.json` | one message to a doctor: `v`, `id`, `to`, `person`, `time`, `kid` readable for routing; `status: "queued"`, `queuedAt`, `encrypted: true`; `body` sealed for the flight surgeon's public key (ECDH P-256 with a fresh key per message, HKDF-SHA-256, AES-256-GCM; the readable fields are bound to the seal). Written whole, then renamed, so it is never seen half-written. |
| `data/study/study-alerts.csv`, `data/study/study-subjects.csv` | written only when someone runs `node tools/study-export.mjs`: the alert steps and a summary per subject, by id only, with no alert about the mind, the cycle, symptoms or medicines; inside the data folder, so the server never serves them |

`DATA_DIR` moves both. This version seals for the DEMO key pair in `demo-keys/`, which is public and not a real key; `node tools/read-outbox.mjs` opens the queue as the ground would. Without a key, a message to the doctor on board is still kept and one to Earth is refused. Nothing sends the outbox yet: the downlink is not part of this program.

### Kept only in this browser

| Key | What |
|---|---|
| `jff-crew-ui-v1` | screen settings: the switches, messages read on this computer, the example flight, the mission profile, the crew's own mission. "Sound off" and the drill are not kept: sound is on and the drill off at every sign-in. What was read and acknowledged is also in the person's record (`alert` events), which every screen of the person reads |
| `jff-crew-waiting-v1` | records entered while the station server did not answer; sent when it answers again |
| `jff-theme` | dark, light, or follow the device |
| `jff-pin-v1:<id>` | the optional PIN, only as a salted PBKDF2-HMAC-SHA256 hash (600,000 iterations, 16-byte salt) |
| `jff-mind-private-v1:<id>` | the private journal, the plan for hard days, worksheets and Earth breaks |

## How to add a new measure

1. **A cell in `src/config.js` (`CELLS`).** Give it a unique `indicator`, an `id` (the team's letter, or `null`), a `label`, a `section` (`body`, `tests`, `complex`, `camera`, `psyche` or `env`), a `kind` (`KIND.NUMBER`, `PANEL`, `COMPLEX`, `CAMERA` or `SELF`) and an `effort` (`light`, `high` or `extreme`). A number cell also needs a `unit`, a `normType` with its `norm` (`range`, `below-both`, `min-parts`, `baseline-percent`, or `record` when no checked norm exists), `compareWith`, one of the four norms (`earthGeneral`, `spaceGeneral`, `personalEarth`, `personalSpace`), and `norms` with the text of each. Optional: `atRest`, `allowNegative`, `reviewByAi`, `private`, `scale`, `answers`.
2. **The source of the norm.** Add `{ name, url }` to the source tables at the top of `config.js` and point the norm at it with `src`. A norm without a checked source stays out: use `record`. The cells added after the night's NASA-style reviews (written by Claude in the roles of NASA reviewers, not by NASA) also say where the measure is available on the ISS (`availability`, `availabilitySrc`); a new cell should too.
3. **Red limits, only with a published value.** `red: [{ when, value, level, source, url, note, draft: true }]`, with `when` one of `below`, `atOrBelow`, `above`, `atOrAbove` and `level` `action` or `urgent`; `part` picks one number of a pair, `atRest` skips the limit during exercise. A value just past a limit must be outside the norm.
4. **A simulated source in `SOURCES`**, so the technical view can send it and the checks can try its presets.
5. **What follows by itself.** The server accepts the new measure (it checks readings against `CELLS`), and the technical view lists the cell and its source. On the crew screen, a number or self-report cell of the body or the mind shows up under "Other measures" until it is added to a group in `GROUPS` (`src/crew.js`); a cabin cell (`env`) shows under "Cabin air"; a private or complex cell shows only where `src/crew.js` places it.
6. **Optional, for a complete page:** an icon (`ICON_FOR`) and search words (`WORDS`) in `src/crew.js`; the "?" text in `PROVENANCE` (`src/tips.js`); `EXPECTED_EVERY_DAYS`, `SLOW_MEASURES` or `VITAL_SIGNS` in `src/state-levels.js`; plausibility limits in `PLAUSIBLE` of `src/crew.js` (apart from blood pressure, the hand-entry form appears only for a measure listed there) and of `src/csv-import.js` (files and Bluetooth); a LOINC code in `MEASURES` in `src/fhir.js`, or a reason in `NOT_EXPORTED`.
7. **Run `npm test`.** The tests require a known kind, a norm with data for number cells, complete and sourced red limits marked as drafts, every number cell either exported to FHIR or named with a reason, and every preset passing the server's check.

## How to add a new device

1. **A parser that turns the device's data into readings** `{ source, indicator, value, unit, time }`, in the cell's unit. The Bluetooth and CSV readers pass every value through the plausibility limits (`isPlausible()` in `src/csv-import.js`), so a value outside a measure's plausible range never becomes a reading; a new reader should too.
   - A Bluetooth device: an entry in `DEVICE_KINDS` in `src/ble.js` (the standard service, its characteristics with a `parse` function, `stream` for continuous values, the `source` id) and a branch in `toReadings()`.
   - A file export: a format in `FORMATS` in `src/csv-import.js` (`id`, `name`, `documented`, `sources`, `find()` to recognise the headers, `extract()` that calls `mapReadings()`).
   - A feed: a module like `src/isslive.js` that answers `{ ok: true, readings }` or `{ ok: false, error }` and never throws.
2. **A row in `CONNECTIONS` in `src/integrations.js`:** `id`, `name`, `status` (`working`, `simulated` or `planned`), `what`, `how` and `sources` (title and link); a working row also says what was `tested` and has an `action` (`connect`, `toggle`, `import`, `open` or `link`); a planned row says who it `needs`. Optional: `note`, `earthDemo`, `personal`. Settings draws the row and its "?" from this entry.
3. **Its source id in `KNOWN_SOURCES`** (`src/integrations.js`), so the "?" text and the FHIR export (Device and Provenance) say where each value came from. An id listed neither there nor in `SOURCES` of `src/config.js` is reported as of unknown origin.
4. **Wire the action in `src/crew.js`:** `connectKind()` for a device, `toggleFeed()` and `readFeed()` for a feed, `importFile()` for a file. Device readings go through `addReading()`; feed and file readings through `toEvents()`, `onlyNew()` and `keep()`.
5. **A new outside address** (a feed) goes into `DATA_SERVICES` in `src/security.js` and into the Content-Security-Policy meta tags of `index.html` and `machine.html`; `tests/pages.test.js` checks that both pages allow every one.
6. **Tests and docs:** a test in `tests/integrations.test.js` with a saved answer in `tests/fixtures/`, and a row in `docs/INTEGRATIONS.md` with its status and sources.

## Open decisions (the team's)

These stay open. Where the code needs an answer to run, it carries a draft marked for the team.

| Open decision | Where it shows in the code today |
|---|---|
| Which questionnaire for the mind | none is added; open question 8 |
| Whether to use a NEWS2 total score | only NEWS2's single red values are used (`NEWS2_NOTE` in `src/config.js`) |
| The rule for immediate danger in the AI session | the crew screen sends nothing by itself and says this is the team's decision; a draft rule waits in `crisisNotice()` (`src/support.js`), marked "TO CONFIRM" by `renderCrisisNotice()`, which no page shows yet |
| The AI's name | "AI support, not a psychologist" for now |
| "Anonymous" or "private" | the panel is called "Anonymous session with AI support" |
| The level thresholds, including the mind (6 and 8 low days of the last 14) and the watch rule (3 readings in a row) | `RULES` in `src/state-levels.js`, all drafts |
| Names for crew members 3 and 4 | "Crew member 3" and "Crew member 4" in `CREW` |
| Who gives advice: the automation or the AI | open question 6 |
| How the program tells people apart | a sign-in card and an optional PIN in one browser; the server has no sign-in and no roles |
| Anonymity before "Message the doctor" | the message carries the person's id, readable in the outbox for routing |
| Who analyses X-rays and other complex data | open question 3 |
| The default with no doctor and no link | open question 5; draft: the crew on board is alerted and the doctor's message is queued |
| Turning the ISS O2 value into the inspired value | cabin O2 from ISSLive is shown on its row but not saved; `inspiredO2()` in `src/isslive.js` does the conversion if the team chooses it |
| An upper heart rate limit during exercise | none; limits marked `atRest` are skipped for exercise readings |
| A resting pulse of 40 for athletes | the red limit is "at or below 40 bpm, urgent" (NEWS2), with a note that trained athletes can rest at 40 to 60 |
| How long a red reading of a rarely taken measure stays | it stays while it is the latest reading of that measure |
| An ISS-specific cabin pressure limit | the red limit is NASA-STD-3001's 34.5 kPa; the ISS's own 65.3 kPa is only in the note |
| How long a drill may run, and whether one screen's drill should reach every crew screen | it ends by itself after 60 minutes (`DRILL_RULES.maxMinutes`, a draft with no public source), at sign-out and by hand; it is turned on per screen |
| Which alarms ask for a workload rating, and which Bedford limit applies to answering one | urgent ones, once acknowledged (`WORKLOAD_RULES`, a draft); the export counts ratings above 3 and above 6 ([V2 5007]: 3 or less for nominal tasks, 6 or less under degraded system conditions) |
| What counts as acknowledging an alert | the first of Mark as read, Mark all as read, the Messages key, Silence and "Silence all sounds", or "I am okay: false alarm"; the Messages key acknowledges every alert listed |
